# ffemu: design decisions and findings

Notes for a Claude Code session working on ffemu, the emulator of the FlashFloppy user interface in `ffemu/`. This file is the owner's: it is tracked on the branch `private` alone, like `ffemu/build.sh`, and must not get into a pull request. `ffemu/README.md` is the user documentation; this file records why things are as they are, and what was found out the hard way. The build, test and branch rules are in the top-level `CLAUDE.md`.

## Architecture

- Two halves. The firmware half is the firmware's own sources, compiled with the firmware's headers and its own subset of the C library, renamed out of the way of the host's; the host half uses the host C library. Only `emu.h` is shared, so no firmware type or macro leaks into the host code and back.
- The emulated board is an SFRKC30.AT2 (AT32F415), which shares the STM32F105 code; the build level is "debug", for the assertions and the console output.
- Time: a 1 ms tick, delivered as SIGALRM to the thread that runs the firmware. Where the host sleeps only in coarser steps (a VM on a Windows host: 4 to 16 ms), the time is kept by spinning, and the console says so. The check at the start can pass by chance on the Ubuntu VM (steps of 6 to 15 ms, one of five sleeps returning early now and then), which made the display four times slower and a long name scroll slowly, so eight overshooting sleeps in a row also switch to spinning (2026-10-07). The `I2C: Error (0000)` lines once seen on the VM were the deadlock described two items below.
- A power cycle re-executes the program. What survives goes through environment variables: `FFEMU_FLASH`, `FFEMU_STATE`, `FFEMU_USB` (the store of the firmware's writes, as an open file descriptor and its layout hash) and `FFEMU_TTY` (the terminal modes saved at the very first start, so that a crash after any number of power cycles restores the original ones).
- Interrupt handlers run on the firmware's thread, from the tick's signal handler or at the firmware's sync points, never in the middle of an update of the models (`irq_run()` returns while its own thread is in `emu_hw_sync()`): before 2026-10-08 a tick in the middle of one could run the I2C event handler, whose `i2c_stop()` then spun on the STOP bit with the models' lock held by the interrupted update, for ever. On Linux the firmware recovered after its 200 ms `DMA_TIMEOUT`, which showed as `I2C: Error (0000)`; on Cygwin it hung with one core at 100%, seen with gdb in a live session.
- The I2C bus and its DMA also run on a thread of their own (`emu_hw_sync_bus()` every 100 us), concurrently with the firmware, so that a handler waiting on the bus does not depend on a nested tick: Cygwin defers a signal to a thread that spins inside a handler until it calls into Cygwin, which a register poll never does. With nested ticks disabled in a test build, the display hung at once without this thread and ran with it. The models' changes to registers that the firmware also writes are atomic (`reg_update()`). The one-shot timer and GPIO stay on the firmware's thread: the timer's end clearing CEN would race the firmware setting the next deadline.
- A crash signal ends with `_exit(128 + sig)` after restoring the terminal: re-raising the signal from inside the tick handler gave exit status 0 on Cygwin.
- The firmware's `snprintf()` has no `%.*s`: copy into a bounded buffer first.
- Two programs from one source: `make TARGET=shugart|apple2`, giving `ffemu` and `ffemu-apple2`, each with its own build directory and its own directories of settings and logs (named by `FFEMU_NAME`), so that both can run at once, with flash mirrors of their own like two Goteks. The Status window shows the target in bright green; the top line has the program name only (a green target there was dropped on 2026-10-07: the FDD rows of Controls show the kind of controller anyway). ffemu writes "Apple2" with an Arabic 2 (the owner's word of 2026-10-07): Apple's own names have many flavors of the Roman II. Since the universal firmware (`apple2-auto`, 2026-10-08) `ffemu` runs the shugart firmware with both modes, and `ffemu-apple2` the apple2 firmware with its one mode; `FFEMU_APPLE2` now means only that the FDD type is fixed.
- A debug build moves stepper phases 0 and 1 onto the rotary encoder pins (PA6, PA15) and turns off the KC30 header, since PA9/PA10 are the UART; with the universal firmware this holds for the shugart target too. ffemu compiles `src/gotek/board.c` and `src/floppy.c` (which includes `gotek/floppy.c`) at `LEVEL_logfile` (`-ULEVEL -DLEVEL=LEVEL_logfile`) in both programs, which gives the release's pins with no firmware patch; the level is tested in `inc/` only for `ASSERT()` and prototypes, so one file can differ. The owner does not want this mode on a real Gotek, so no firmware option for it.

## Settings and the flash mirror

- FF.CFG is written as the Flash mem dialog shows it, its edits applied to the flash memory's configuration (`fd_edited()`; until 2026-10-10 the buttons wrote the flash as it was, so an edit made before Save went into flash by OK and was overridden on the restart by the file just saved, which the owner hit with `display-type = auto`), by the two buttons of the dialog (2026-10-09, the owner's wish, with the .BAK and the comments his requirements): `cfgfile.c` walks the firmware's `examples/FF.CFG`, built into the program as a string by `mk_text.py`, and emits each option line with the value `emu_flash_option()` formats, below the comment lines that precede it in the example; the full file keeps the example's headers and blank lines, the diff-from-flash file ("non-defaults" until 2026-10-10, when it also named the options differing from the defaults) only the commented options, one blank line after each. The first version looped for ever on a CR LF line, having dropped the CR from the step as well as from the length: the step must come from the full line. The write goes to `FF.CFG.new`, then the old file to `.BAK`, then the rename, so that a failure leaves the old file in place. A real drive is written through the system, where it is mounted: `usb_disk_mount()` in `usbdisk.c` gives the first drive letter of the partition on Cygwin (`J:/`, which the C library takes as a path) or the mount point from `/proc/mounts` on Linux, and the re-insert afterwards drops the firmware's overlay, so the new directory sectors are what it reads; tested on the owner's stick on 2026-10-09 (the file written and removed again). An image file is not written, since that would need a FAT writer; a red message box over the dialog says so, as it does for an unmounted disk and for a value an option does not take (the owner's word of 2026-10-09: the red text on the bottom line that these used before was too easy to miss). The box is a dialog state of its own, `DLG_message`, drawn over the dialog it came from and closed by Enter, Esc or Space back to it, in the style of the "Window too small for dialog." box: no key help, the text a sentence ending in a period (the owner's word); its text wraps at blanks to the window's width. The two FF.CFG buttons stand one over the other at the right among the controls, two rows above the OK and Cancel row (the owner's wish); OK and Cancel keep their old places.
- IMAGE_A.CFG in Status (2026-10-09): `usb_read_text()` finds the file in the FF folder or the root through the same small FAT reader that reads FF.CFG from an image, now able to read the live volume with the overlay (`vol.live`, sectors through `get_sectors()`), and re-reads it when the drive's write count or the FF.CFG generation changes. The firmware writes `\EJ` into it on an eject, so the line shows that literally after Enter on a mounted image; a missing file shows as `absent`, a file of blanks only as `empty`, both in dark gray (the owner's wording).
- `ffemurc` in `${XDG_CONFIG_HOME:-~/.config}/ffemu/`, the console log in `${XDG_STATE_HOME:-~/.local/state}/ffemu/`; under sudo both follow `SUDO_USER`'s home and are chowned to `SUDO_UID`/`SUDO_GID`.
- The flash memory is mirrored in the `[Flash mem]` section at the end of `ffemurc`: `hex = ...` with the bytes, then all options in FF.CFG syntax. Loading applies the hex, then the options on top; an option that differs from the hex wins, with a warning. A value that no FF.CFG text expresses is written as `0x...`, or noted as only in the hex. The round trip was fuzzed with 440 random flash images, with no difference.
- The section is rewritten whenever the firmware writes its flash, which it does when it reads an FF.CFG that differs. Consequence for testing: a test drive with an FF.CFG overwrites the flash mirror of whatever `ffemurc` the run uses. Tests must set `XDG_CONFIG_HOME` and `XDG_STATE_HOME` to a directory of their own; on 2026-10-07 a test run on the VM did not, and the VM's real flash mirror was lost.
- `display-type` must be decoded with the OLED bit tested first: bit 0 means `narrower` when the OLED bit is set, something else for an LCD.

## Display

- The controller model is an SSD1306 or SH1106 as an I2C slave, with 132 columns of RAM; the SH1106 reads RAM after a dummy byte and shows columns from offset 2. The firmware tells the controller by itself and takes the panel height from `display-type`, so a mismatch between the fitted display and the flash is possible and is shown as "display type mismatch".
- The 7-segment LED display (2026-10-09, the owner's wish; his ASCII render of a digit, 10 by 7 with the point and the upper half a column right of the lower, is the shape): `led7seg.c` models the TM1651, 3 digits, with START and STOP on DAT while CLK is high, bytes LSB first and the ACK pulled on DAT while CLK is low after the eighth bit, which the firmware's probe relies on and which `hw.c` feeds back into port B's input register; and the pair of 74HC164, 2 digits, 16 bits on CLK's rising edges, taken once CLK has rested 50 us. The lines are PB6 and PB7, the I2C1 pins, their levels computed in `hw.c` from port B's CRL and an output register kept from the firmware's BSRR and BRR writes: an input or an alternate function reads high, a plain output its ODR bit. The digits are fonts in `led_font.h`, one per rendering, each row a string literal of segment numbers, the firmware's bit order a to g and the point, and dots for empty, one digit wide with its gap (the owner's form, 2026-10-10; his sketch's `D()` around each row was an example, not a wish, and a first version that took it literally lasted an hour); they were generated once by `gen_led_font.py` in the scratchpad from the parametric digit of the first version, segments t thick, verticals 5t/2 long, the upper half shifted t right, the point t right of the lower frame, digits 2t apart, t = 1, 2 and 4 for ASCII, half blocks and Braille, so the ASCII font is the owner's pattern exactly and the Braille one is 32 dots high; `draw_pixels()` draws the OLED too now. Unlit segments are drawn in dark gray on a terminal with 16 colors, as the faint segments of a real display. The display drawn is `fitted_display`, set at start: `config.display` is the one chosen, which differs between the choice and the restart, and drawing by it read the LED model with no digits and overran the pixel buffers, found by the test of the rows dialog. The firmware looks for an LED display only with `display-type = auto`; `test_data/FF.CFG` sets `oled-128x32`, so a test of the LED display needs a drive without that line (`led_data/` in the scratchpad, a copy of `test_data/`), and with `test_data/` the display comes up "off - display type mismatch" after the firmware re-reads FF.CFG, as the device would. The 2-digit display stays blank for `display-probe-ms`, 3 s, while the firmware keeps probing for a 3-digit one. Verified by `dump` ("000", "001" after Right, "E31" from a bad image) and by tmux shots of the three renderings and the dialogs (`ledshot.sh`, `ledrows.sh`, `ledtest.sh` in the scratchpad).
- Both directions offer to reconcile: changing the display (key 0) offers to change `display-type` in flash, and since 2026-10-10 in FF.CFG on the drive as well when the file sets it (`ff_cfg_file_option()` reads the value through the volume, `ff_cfg_set_option()` rewrites the one line in a directory's or a mounted disk's file, .BAK kept), the dialog saying so in a third line; for an image, which cannot be written, the line warns that the file will override the change on boot. Before that the owner saw the device restart twice and end in the mismatch, FF.CFG undoing the dialog's change on the next boot. Errors are bright magenta since the same day (the owner's word): message boxes white on bright magenta (`CP_warn`), the mismatch note and the too-small hints bright magenta (`CP_note`), and the display's frame widens to its title, `frame_width()`, six columns beyond the text for the title's blanks and the corners; changing `display-type` in the Flash mem dialog (key 9) offers to fit the display of the same controller with the matching height. An LCD `display-type` has no emulated display, so nothing is offered.

## Terminal user interface

- Turbo Vision colors. Every color pair has a bright twin at +64, using colors 8 to 15 explicitly: GNOME Terminal does not render bold as bright.
- Characters: U+25A0 to U+25FF (squares, triangles) render double-width in Ubuntu Mono and in the owner's Windows Terminal font, so they are banned. Scroll marks are ASCII `^` and `v` in green, the scroll bar is U+2592 with a U+2588 thumb; the radio bullet U+2022 is fine on both. A non-printable byte in a pane shows as `?` in bright magenta; CRLF lines are shown without the CR; a line cut short ends in a green `>`, drawn after the scroll bar so that it stays visible.
- Esc acts after 25 ms, htop's value, or 200 ms when `SSH_TTY` is set, unless `ESCDELAY` is in the environment (the owner's word of 2026-10-09: it was 200 ms everywhere, set for ssh, and he found the wait annoying; at a flat 25 ms he got stray Esc presses over ssh within the hour, so the ssh case keeps its 200 ms). Modern toolkits such as Bubble Tea and crossterm wait not at all and parse by read boundaries; ncurses programs set 25 ms; Midnight Commander keeps a second since Esc is a prefix key there.
- A terminal reports key presses but not releases: a press holds its virtual button for `hold-ms` (150 ms), and Space starts the latch mode, in which keys toggle buttons, for long and combined presses.
- The FF.CFG pane scrolls with Ctrl+PgUp/PgDn: Shift+PgUp/PgDn is taken by Windows Terminal for its own scrollback.
- Dialogs fit a 99-column terminal (the Flash mem dialog is 96 wide, in columns of 31/31/26); when the window is smaller, a red "Window too small for dialog." replaces the dialog.
- The console log file is byte-perfect; only the pane substitutes characters.
- The FF.CFG pane stays while the drive is out, dimmed (dark yellow, dark magenta, dark gray frame; the owner's wish of 2026-10-08): a directory's file as it is on the host now, looked for and read again on every Del (a generation counter in `usb_info` forces the re-read even when size and time did not change); an image's or disk's as last read, kept with the removed image (`grave`) until the next removal.
- Keys light up for the hold time when pressed, in the latch key's colors: Ins, Del, Home in the list, the FDD keys, and the paging keys in window frames (Ctrl too with Ctrl+PgUp/PgDn).
- The owner's color scheme of 2026-10-08, arrived at by many trials in wt, plain Git Bash and plain Ubuntu, "now art": keys red (`CP_key`: bright, dark where dimmed; dialog hotkeys red too), values yellow; a key or button in use dark red on bright yellow (`CP_ctl_on`, which also serves a button held in latch mode); latchable buttons at rest in latch mode dark red on light gray; buttons at rest bright red on the window's dark blue, in light gray parentheses, round as on the Gotek: `(<)` `(>)` `(Ent)`. Tried and rejected: brackets, bright blue and dark cyan paper. The arrows `^` and `v` have no parentheses and stand one column right of the knob's middle, over the `t` of `Ent`, deliberately: the rim moves up there when the knob turns anticlockwise, down when clockwise; never center them. Active FDD signals black on dark yellow; the USB port dark yellow on access; "Ejected" and "None" dark gray. In Status, states and values are bright green and labels and punctuation light gray, in the lines of the drive (`Cyl 2, side 0, selected`) and of the USB drive (`2 files, 0 dirs`). Status says `Cyl` and `Floppy` (not `Image`, which the USB drive's image would confuse): capitalized words, the 80s style of the TUI.

## The USB drive from a directory

- Always FAT32: 512-byte sectors, 8 per cluster, 32 reserved sectors, 2 FATs, at least 66'000 clusters (fewer than 65'525 would make it FAT16) plus 4'096 free for the firmware's own files. Directories are placed first, so that the firmware's directory scans stay within a small part of the volume. File contents are read from the host on demand. Entries are sorted by byte order of the path, so that the volume, and the layout hash that keeps the firmware's writes across power cycles, is reproducible; the real order on a stick is the copying order and is ignored.
- The firmware's writes go to an unnamed temporary file of records (sector number and contents), passed across the re-execution as an open file. It is accessed with `lseek()` and `read()`/`write()`, because the Cygwin runtime refuses `pread()`/`pwrite()` on a file inherited across `exec`.
- The aim is that the firmware sees what it would see on a real stick with the files copied to it, so the FAT details follow the host system: Windows when built for Cygwin/MSYS2, Linux otherwise.
- Windows short names model its FAT driver (`RtlGenerate8dot3Name()`): characters in the OEM code page (`GetOEMCP()`), tails `~1` to `~4`, then two characters, a 4-digit hash of the long name and `~1`. Checked against `dir /x` on NTFS, which uses the same generator:
  - The hash is computed from the long name in its original case; the algorithm is reproduced in `nt_checksum()`.
  - A name whose base gives fewer than 3 characters gets the hash at once: `a b.txt` becomes `AB5079~1.TXT`.
  - A dot that only dots and spaces precede does not start an extension: `.gitignore` becomes `GITIGN~1`.
  - NTFS skips non-ASCII characters (extended characters are off there); for FAT they are kept in the OEM code page, and skipped when the code page lacks them. Not verified on a real FAT volume.
  - A name that is a valid 8.3 name in one case per part gets no long name: the case goes into byte 12 (0x08 base, 0x10 extension). Any non-ASCII character makes a long name. The latter is a recollection of fastfat's `FatEvaluateNameCase()`, not verified.
- Linux short names model `vfat_create_shortname()` with the Ubuntu defaults: code page 437 (`CONFIG_FAT_DEFAULT_CODEPAGE=437`), `shortname=mixed`. A long name is written unless the name is all capitals and ASCII; tails `~1` to `~9`, then a random number, replaced here by the Windows hash for reproducibility. Checked byte for byte against a loop-mounted vfat image with files copied by `cp`, including the code page 437 upcasing of accented letters.
- Names left out, with a console message: trailing spaces (vfat refuses them, checked; Windows cannot make them), trailing dots on Windows (Linux strips them instead), names equal to another one in the folder but for letter case (possible only on Linux; the first in byte order stays), special files, files of 4 GB or more, more than 50'000 entries or 12 folder levels.
- Attributes: read-only from the host; on Windows also hidden and system, via `GetFileAttributesW()`. On Linux, vfat marks a file read-only when no one may write it (`fat_mode_can_hold_ro()`, never for a directory), but plain `cp` does not carry the mode over; `cp -p` and copying file managers do.

## The USB drive from an image or a disk

- The argument may be a regular file (an image of a whole drive) or a block device. Sectors are read when the firmware asks, in runs; the firmware's writes go to the same temporary store, never to the image or the disk.
- FF.CFG for the panes is found by a small FAT reader that finds the volume as FatFS does (`check_fs()` and `find_volume()` of the firmware's FatFS: sector 0, else the first of the four MBR partitions that holds a FAT volume; no GPT), FAT12, FAT16 or FAT32. It matches short names only, so `ff.cfg` written by Linux shows as `FF.CFG`.
- On Cygwin/MSYS2, `/dev/sdX` is `\\.\PhysicalDriveN`, `sda` being drive 0, and `cat /proc/partitions` shows the drive letters. Opening one needs a terminal started as administrator; on Linux, sudo. ffemu says so on EACCES/EPERM.
- The USB drive attached, the default drive of a run without an argument since 2026-10-08, before that the argument `usb:` (`usbdisk.c`, 2026-10-08): the whole disks of `/proc/partitions` (Cygwin has it too, with drive letters), empty ones left out (card reader slots show size 0); on USB per `/sys/block/<name>` resolving through a USB device on Linux, per `IOCTL_STORAGE_QUERY_PROPERTY` bus type on Windows, which needs no administrator rights (opening the drive with access 0). A drive is given as its first partition (`/dev/sdf1`): Windows lets an ordinary user read a volume on removable media but not `\\.\PhysicalDriveN`, which the owner found by trying; the partition starts with the FAT VBR, which ffemu's volume reader and FatFS accept at sector 0. One drive is taken, several are listed one a line ending with `... is /dev/sdX1` and ffemu stops; none gives a line asking for a directory, an image or a disk. A denied whole disk on Windows gets a hint to give its partition. Tested on Windows with one stick (J:, `/dev/sdf`) and on the VM with none; the list of several and a Linux stick are untested.
- A lock serializes sector access, so that the script command `save <file>`, which writes the drive as the firmware sees it, can run while the firmware does.

## The floppy interface

- The keyboard stands in for the host computer's signals (`emu_in_fdd`, STEP pulses counted in `emu_in_step`), shown in two FDD rows of Controls; the owner's design of 2026-10-07. The second row starts with the kind of controller on the other side of the cable, `Step/Dir` or `Apple2` (not `Shugart`, which the `interface` option could contradict).
- The FDD type (2026-10-08, the owner's wish): `emu_fdd_type` in `emu.h`, chosen in the dialog on key 8, kept as `fdd-type` in `ffemurc`, with the script command `fdd-type`; `hw.c` drives the pins of that type, and both the STEP and the WDATA-capture interrupts are routed, since the firmware primes the one of its mode. A change power-cycles the device, which detects the mode at boot, and puts the signals back to the type's defaults (`ui_fdd_set_type()`), since a DIR left active or phases left on would carry over. Status labels the drive with the mode the firmware detected (`emu_fdd_status()` returns it) in place of the word `FDD`, so that a detection that went wrong shows against the type in Controls; the label took the place of a prefix because `Step/Dir: Cyl 0, side 0, selected` did not fit the pane at 99 columns. The firmware's log says `Apple2 on (200/200/200/200 200ms)`, the counts of samples with each phase input low and the window. The bottom line is the owner's text of 2026-10-08, items two spaces apart: `Esc Exit  Q/W/E Rendering  Ctrl+L Refresh  [Shift+]1..7 Color  8 FDD  9 Flash mem  0 Display`, 93 columns; when the window is narrower it ends in a bright green `>` (`CP_bar_crop`, green on the bar's light gray). Ctrl+L, a resize and a change of rendering set `clearok()`, so the next refresh repaints the whole screen: Windows Terminal left parts of it stale after maximizing. The dialog describes the types as `Shugart (Beta Disk), IBM PC and the like` and `Apple Disk II, Pravetz/Agat (Izot) 140K`, his words. In `ffemu-apple2` the key does nothing and is not listed.
- The console pane's up mark means "lines hidden above, or older output than the 8 KB tail buffer holds"; until 2026-10-08 the second test compared a length that had just lost its final newline, so the mark was always on. A lit signal, black on dark yellow so as not to look like a pressed key or a latched button, means active as on the schematics, not a high voltage: DIR is active-low, and active steps inward. Defaults: drive selected or enabled, DIR active, so that steps go to higher tracks. The signals and the Apple2 phase state survive a power cycle, in `FFEMU_STATE`.
- ffemu only supplies signals; what they do is up to the firmware, whose own `src/floppy.c` (with `floppy_generic.c` and `gotek/floppy.c`) ffemu compiles since step B (2026-10-08); step A had copied its handlers into `stubs.c`. The firmware commit before it gives `gotek/floppy.c` C fallbacks under `#if defined(__arm__)` / `#else`: a C SELA entry calling the handler a flag chooses instead of the self-patching ARM stub (which also defines `gpio_out_active` and `gpiob_setreset`), an atomic word update instead of the bitband store, `uintptr_t` casts; all 66 firmware images were built before and after with `SOURCE_DATE_EPOCH=0` on the VM and compared byte for byte, identical. In `hw.c`: the signals on their pins, active low except the Apple2 stepper phases, which `POLL_step()` reads as active high (driving them low made a phase read on when off); EXTI per line as AFIO routes it, which the rotary encoder needs since `board_floppy_init()` reroutes lines 4 to 7 to port B and the rotary setup then routes PA6 and PA15 back; the EXTI pending register as the model's own bits plus a reserved mark bit, since the firmware clears it by writing ones; TIM2 capturing the end of each STEP pulse, a pulse lasting from one sync to the next. The read and write data timers and DMA are mere registers, so no data flows and no index pulses come; the firmware logs an occasional `Trk 0: late ...us`. `objcopy` renames `floppy_handle()`, `floppy_insert()` and `floppy_cancel()`, and `stubs.c` wraps them: an idle of 1 ms per pass of the loop that runs while an image is mounted, which the device runs at full speed, and the image name for Status. The Apple2 build compiles `src/floppy.c` at the logfile level, like `board.c`, for the release's phase pins. CPU stays at about 9% of a core with an image mounted.
- Apple2: `+` and `-` go through the cycle of eight states that DOS 3.3 RWTS goes through, single phases and the pairs between them, one state per press, so that two presses make one step (the firmware steps only on a single phase next to `cyl & 3`), which the owner wants for seeing how it works; the 307 firmware shows the phases on the display. `\` releases all phases and keeps the state, shown as `01..` in bright green right of the phases, as RWTS keeps its current half-track and starts the next seek from it. Without D_E, the phases are ignored, as the Disk II drive gates them with its enable.
- Keys: `[` `]` `-` `+` `\`, also `=` for `+` and `/` for `\` (the Russian layout types `/` there) and the Russian letters on the keys of `[` and `]`.

## Firmware findings

- The OLED buffer overrun: `read_ff_cfg()` changes `ff_cfg.oled_font` before the reset, while the display keeps refreshing with the old `lcd_columns`; 6x13 to 8x16 writes up to 40 bytes past `buffer[]`. In ffemu it hung the UI. Fixed on `fixes`, upstream #1073.
- FatFS here: `FF_CODE_PAGE` 437, `FF_USE_LFN` 1, `FF_LFN_UNICODE` 0, no exFAT. A long name that does not convert to code page 437 makes FatFS give the short name as the name, case flags applied (seen as `____~1`). So on a stick written by a Russian Windows, Cyrillic names reach the firmware as their short names in code page 866. The font renders only 0x20 to 0x7E.
- The firmware skips names that start with a dot and hidden entries, write-protects read-only images, and stores the path in `IMAGE_A.CFG` with long names.
- On the first mount the firmware reads about 6'500 sectors within 1.5 s, in either drive mode: its own scanning, not ffemu's.

## Testing techniques

- Windows short names: create the names on NTFS in byte order and compare with `cmd //c "dir /x"`.
- Linux short names: on the VM, a vfat image mounted with `-o loop,uid=...,gid=...,utf8=1` (passwordless sudo works there), files copied one by one in byte order, then the directory entries of that image and of ffemu's `save`d volume listed and diffed.
- The disk mode: a loop device of an image, under sudo.
- The firmware build of each commit: a `git clone --shared` on the VM, so that the work tree and `~/retro/flashfloppy-build/` stay untouched.
- A live ffemu that misbehaves: MSYS2's `gdb` (installed 2026-10-08 with the owner's consent) attaches by the MSYS2 PID (`ps` in MSYS2 shows it beside the Windows one), takes `thread apply all bt` and detaches, leaving it running. Its executable on disk has usually been rebuilt meanwhile, so the symbols come from a rebuild of the exact commit it reports, in a `git worktree` at that commit built with `O=` into the scratchpad. CPU per thread: PowerShell's `Get-Process -Id <Windows PID>`, `.Threads`, `TotalProcessorTime`.
- A hang that depends on when signals come: a scratch build of the ffemu sources whose `on_tick()` returns while `irq_depth` is set, so that no nested tick ever comes, as on Cygwin at its worst, made the I2C hang happen at once, and showed what each half of its fix does.
- That a firmware change leaves the device's firmware alone: build every target and level from `HEAD` with and without it, in two `git clone --shared` on the VM, with `SOURCE_DATE_EPOCH=0` for the build date, and compare every `.bin`, `.hex` and `.upd` (66 files).
- Colors as drawn: `tmux capture-pane -e -p` keeps the escape sequences (`ESC[92m` bright green ink, `ESC[103m` bright yellow paper, and so on).
- This Windows machine has "Use Unicode UTF-8 for worldwide language support" on, so its OEM code page is 65001 and ffemu writes UTF-8 bytes into short names here. Whether the FAT driver of Windows does the same is not verified; a real stick in the disk mode would show it.

## The release binaries

- Windows: `ffemu.exe` from MSYS2 needs only `msys-2.0.dll`, so it runs in Git Bash.
- Linux: built on Ubuntu 22.04; needs glibc 2.34 or later and `libncursesw6`/`libtinfo6`, which are "Priority: required" in Ubuntu, so it runs on a stock 22.04 or later on x86-64, not on 20.04. Shipped as a tarball to keep the executable bit.
- GitHub serves release assets as `application/octet-stream`; an image in the release notes linked to an asset depends on the browser sniffing it.
- A release has four binaries, `ffemu-<version>-windows.exe`, `ffemu-apple2-<version>-windows.exe`, `ffemu-<version>-linux-x86_64.tar.gz` and `ffemu-apple2-<version>-linux-x86_64.tar.gz`, each tarball holding just its executable, all built from the tagged commit and reporting its hash (1.1 was built from `mine`, which is why it was withdrawn). The owner's screenshot comes from the VM, where Ubuntu saves Alt+PrtSc in `~/Pictures/Screenshots/`; it is attached to the release as `ffemu-apple2-ubuntu-screenshot.png` and linked from the notes with a `?v=` query string.
- Updating a draft release through the API (`PATCH .../releases/<id>`) without `tag_name` resets its tag name to `untagged-...`, and publishing it then creates no tag: v1.1 went out so and had to be retagged. Always pass `tag_name`.
- A release asset URL requested before its tag exists stays a cached 404 for a while; a query string such as `?v=1` in the image link of the notes gets past it.
- The owner edits release notes on GitHub, which saves them with CRLF: read the body back, and change only what is needed on top of it.
